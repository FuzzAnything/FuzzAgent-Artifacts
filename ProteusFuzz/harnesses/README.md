# ProteusFuzz Harnesses

Fuzzing harness source files generated by ProteusFuzz, organized by run (`round_1` ~ `round_5`)
and by target library. Each directory `round_N/<lib>/` contains the **final** harness dispatcher
of that 24-hour end-to-end run.

## Structure

Each run's harnesses live in one directory:

- `1.c`, `2.c`, … (`N.c`, or `N.cpp` for C++ targets: libpng, pugixml, re2, tinygltf) — one
  generated harness per file. Every file defines its own entry point
  `LLVMFuzzerTestOneInput_N` (matching its file number) and follows the
  `// This fuzz driver is generated for library <lib>, aiming to fuzz the following functions:`
  comment convention, listing the targeted library APIs.
- `entry.c` (`entry.cpp`) — the dispatcher entry point. It declares every
  `LLVMFuzzerTestOneInput_N`, defines `LLVMFuzzerTestOneInput` which reads the harness selector
  from **byte 0** of the fuzzer input and routes via `switch (driverIndex % N)`, where `N` is
  the number of harnesses. The rest of the input is passed to the selected harness as its data.
- `build_cov_synthesized_driver.sh` — the exact compile command used to build the
  source-based-coverage dispatcher binary for this run (see below).
- `run-provenance.json` — the library source commit, target archive sha256, and the original
  experiment paths of this run's dispatcher and coverage binary.

Harness counts vary per run (e.g. libpcap has 52/59/62/53/48 harness sources across the 5
rounds; re2 has 2). Because ProteusFuzz **extends the harness set at runtime** when coverage
stalls, some runs end with more harness files than they started with: in those runs the final
dispatcher is the union of the initially generated harnesses and the adaptively generated ones
(the added files are consecutive new numbers, e.g. `49.c`, `50.c` after `48.c`).

## Compile command

The dispatcher is compiled as a single libFuzzer binary, linking the *coverage-instrumented*
static library archive(s) of the target. The per-run script in each directory records the
verbatim command; schematically:

```bash
clang <dispatcher_dir>/*.c -o cov_synthesized_driver \
    -fprofile-instr-generate -fcoverage-mapping -fsanitize=fuzzer -g \
    -I<library sources / build include dirs> \
    -L<build_cov/lib> -Wl,--start-group <coverage archives> -Wl,--end-group
```

(Use `clang++` and `*.cpp` for the C++ targets; re2 additionally links the bundled abseil
archives from its build tree.) The library itself is built with the scripts in
[../build/](../build/README.md) at the pinned source commit recorded in
`run-provenance.json` / `build-manifest.json`.

Note: harnesses that include the library's headers directly (rather than only the installed
API headers) can produce multiple-definition errors at link time, since the same inline
functions are compiled into the library archive — tinygltf `round_5` needs
`-Wl,--allow-multiple-definition` for this reason (already included in its script).

To rebuild a driver, replace the absolute paths in `build_cov_synthesized_driver.sh` with your
own build tree locations (the script as shipped references the original experiment directory);
the sources of the dispatcher itself are the `.c`/`.cpp` files next to the script, so the
`<dispatcher_dir>` glob can simply point at the script's own directory.
