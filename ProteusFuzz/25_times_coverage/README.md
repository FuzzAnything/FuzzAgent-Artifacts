# ProteusFuzz Code Coverage

Per-run code coverage artifacts of ProteusFuzz, organized by run (`round_1` ~ `round_5`) and by
target library. Each `round_N/<lib>/output_1/` holds the coverage of **one full 24-hour
end-to-end run** of that library — there are **5 coverage trials per library** (one per run),
not 25: ProteusFuzz performs one end-to-end campaign per round rather than 25 repeated fuzzing
trials.

We provided both the raw code coverage data
[llvm_cov.profdata](round_1/libpcap/output_1/llvm_cov.profdata) and formatted data
[index.txt](round_1/libpcap/output_1/index.txt) for each project each run.

## How the profile was produced

For each run, the **whole campaign corpus** — every seed accumulated by the fuzzer over the 24
hours, plus every seed injected by the adaptive harness-extension loop — is replayed through
the *final* coverage-instrumented dispatcher binary of that run (built from the harnesses in
[../harnesses/round_N/<lib>/](../harnesses/README.md), linked against the coverage archive from
[../build/<lib>/](../build/README.md)). The resulting `.profraw`s are merged into a single
`llvm_cov.profdata` with `llvm-profdata merge`. The profile therefore reflects the union of
code reached over the entire campaign by the final harness set.

## Exporting the report

To export the code coverage from
[llvm_cov.profdata](round_1/libpcap/output_1/llvm_cov.profdata), use
[llvm-cov](https://llvm.org/docs/CommandGuide/llvm-cov.html) built with llvm-21:

```
llvm-cov report --instr-profile=<path_to_profdata> <cov_driver> --ignore-filename-regex='synthesized/'
```

where `<cov_driver>` is the source-base code coverage instrumented dispatcher binary of that
run (see [../harnesses/round_N/<lib>/build_cov_synthesized_driver.sh](../harnesses/README.md)
for the exact build command, and [../build/<lib>/](../build/README.md) for the library build
scripts). `--ignore-filename-regex='synthesized/'` excludes the harness (dispatcher) sources
themselves from the report — `index.txt` was generated with this filter so it reports library
code only. Without it, the report additionally contains the harness rows.

Note:

- The instrumented binary must match the profile: profiles were produced with LLVM 18.1.8
  instrumentation; any llvm-cov ≥ 18 that supports the profile format can read them (we used
  llvm-21).
- `index.txt` still contains a few build-generated rows for some libraries (e.g.
  `build_cov/grammar.c`/`build_cov/scanner.c` for libpcap, generated by flex/bison, and
  bundled third-party rows such as abseil for re2 or zlib/libjpeg-turbo for libtiff), because
  they are compiled into the library archive. In our paper's evaluation results, we removed
  the code coverage of third-party libraries (e.g. `absl` for `RE2`) and of build-generated
  files when computing library coverage. So the code coverage provided in this directory could
  be lower than the results in our paper.
